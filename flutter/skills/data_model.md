# Flutter Data Model Skill

## Purpose

Generate clean, lightweight Dart data models for features and modules.

Models must support:

- JSON serialization
- `copyWith`
- `Equatable`
- Optional local database configuration

Do not use Freezed.

---

## Packages

Use:

- `equatable`
- `json_annotation`
- `json_serializable`

Do NOT use:

- `freezed`
- `freezed_annotation`

---

## File Naming

Model files must use **snake_case** without `_model` suffix.

The Dart class uses **PascalCase**.

Examples:

```text
user.dart             → User
admin_settings.dart   → AdminSettings
checkout.dart         → Checkout
user_profile.dart     → UserProfile
```

Request models must use the `Request` suffix:

```text
login_request.dart    → LoginRequest
register_request.dart → RegisterRequest
update_profile_request.dart → UpdateProfileRequest
```

Response models must use the `Response` suffix when a dedicated response model is required:

```text
login_response.dart   → LoginResponse
user_response.dart    → UserResponse
```

Do not use:

```text
user_model.dart
user_data.dart
user_model_model.dart
```

unless explicitly required by an existing project convention.

---

## Model Structure

Generate the model inside the owning feature/module:

```text
feature/
└── model/
    ├── user.dart
    └── user.g.dart
```

The `.g.dart` file is generated by `json_serializable`.

Do not manually implement generated files.

---

## Model Rules

Every model should:

- Extend `Equatable`
- Use immutable fields
- Use a `const` constructor when possible
- Provide `fromJson`
- Provide `toJson`
- Provide `copyWith`
- Override `props`

Example:

```dart
import 'package:equatable/equatable.dart';
import 'package:json_annotation/json_annotation.dart';

part 'user.g.dart';

@JsonSerializable()
class User extends Equatable {
  const User({
    required this.id,
    required this.name,
  });

  final int id;
  final String name;

  factory User.fromJson(Map<String, dynamic> json) =>
      _$UserFromJson(json);

  Map<String, dynamic> toJson() => _$UserToJson(this);

  User copyWith({
    int? id,
    String? name,
  }) {
    return User(
      id: id ?? this.id,
      name: name ?? this.name,
    );
  }

  @override
  List<Object?> get props => [
        id,
        name,
      ];
}
```

## JSON Serialization

Use `json_serializable`.

Every JSON-serializable model should contain:

```dart
@JsonSerializable()
```

and:

```dart
factory User.fromJson(Map<String, dynamic> json) =>
    _$UserFromJson(json);

Map<String, dynamic> toJson() => _$UserToJson(this);
```

Use `@JsonKey` when the API field name differs from the Dart field name.

Example:

```dart
@JsonKey(name: 'user_id')
final int userId;
```

Do not manually write repetitive JSON conversion logic.

---

## copyWith

Every model should provide `copyWith`.

Rules:

- Preserve existing values when arguments are omitted.
- Keep the method explicit.
- Do not introduce unnecessary abstractions.
- Handle nullable fields appropriately when `null` must intentionally replace an existing value.

---

## Equatable

Every model must extend:

```dart
Equatable
```

and implement:

```dart
@override
List<Object?> get props => [...];
```

Include all fields that participate in value equality.

---

## Local Database

Local database support is optional.

Only add database configuration when the model is actually persisted locally.

Examples:

- Hive CE
- Local cache
- Offline storage
- Persistent feature data

Do not add database annotations to API-only models.

---

## Hive CE

When Hive CE is required, add the required Hive annotations to the model according to the project's existing configuration.

Example:

```dart
@HiveType(typeId: 1)
@JsonSerializable()
class User extends Equatable {
  const User({
    required this.id,
    required this.name,
  });

  @HiveField(0)
  final int id;

  @HiveField(1)
  final String name;

  factory User.fromJson(Map<String, dynamic> json) =>
      _$UserFromJson(json);

  Map<String, dynamic> toJson() => _$UserToJson(this);

  User copyWith({
    int? id,
    String? name,
  }) {
    return User(
      id: id ?? this.id,
      name: name ?? this.name,
    );
  }

  @override
  List<Object?> get props => [id, name];
}
```

Do not introduce Hive CE automatically.

Only use it when the project requires local persistence.

## Generated Files

Do not manually implement:

```text
*.g.dart
```

Generate them using the project's configured build runner.

Typical command:

```bash
dart run build_runner build --delete-conflicting-outputs
```

## Model Location

Models belong to the owning feature/module.

Example:

```text
lib/
└── features/
    └── profile/
        └── model/
            └── user.dart
```

For a large module:

```text
lib/
└── features/
    └── auth/
        ├── sign_in/
        │   └── model/
        │       └── login_request.dart
        ├── sign_up/
        │   └── model/
        │       └── register_request.dart
        └── model/
            └── user.dart
```

Place the model at the lowest appropriate scope.

Only move a model to `lib/core/` when it is genuinely shared across unrelated features.

---

## Do NOT

- Use Freezed.
- Add `_model` to model filenames.
- Generate unnecessary files.
- Put repository logic inside models.
- Put API calls inside models.
- Put database operations inside models.
- Put business logic inside models.
- Add Hive CE unless persistence requires it.
- Manually implement generated JSON code.
- Create global models for feature-specific data.

---

## Interaction With Other Skills

The Data Model Skill only handles model definitions.

```text
Feature Generator
        │
        └── Data Model Skill
                │
                ├── Model
                ├── JSON serialization
                ├── copyWith
                ├── Equatable
                └── Optional local DB configuration
```

Repositories, APIs, databases, and services are handled by their respective skills.
